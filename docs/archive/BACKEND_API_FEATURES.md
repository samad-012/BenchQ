# JobNavigator Backend Features and Frontend Integration Guide

This document is derived from the backend source code. It covers backend behavior only and is intended to be sufficient for building a frontend client.

## Inventory

- **Backend feature groups:** 20
- **HTTP endpoints:** 119
- **Framework:** FastAPI
- **Persistence:** SQLAlchemy with PostgreSQL in normal deployments (SQLite is supported by parts of the test setup)
- **API base prefix:** `/api` for application endpoints
- **Interactive contract:** `/docs`, `/redoc`, and `/openapi.json`

The feature count groups related behavior into frontend-sized capabilities. The endpoint count is the literal count of FastAPI route decorators in `backend/main.py` and `backend/api/routes_*.py`, including the health route, two tracer routes, and the hidden root tracer route.

## Client-wide contract

### Authentication

All endpoints require authentication except `/health`, `/docs`, `/redoc`, `/openapi.json`, `/cv/{token}`, `/?cv={token}`, `/api/telegram/webhook`, and the three `/api/auth/*` routes.

A client can authenticate in either of these ways:

- Send `X-API-Key: <dashboard_api_key>` on each request. This is appropriate for the browser extension and API clients.
- Call `POST /api/auth/set-session`, then send the resulting `jn_session` HTTP-only cookie. Browser requests must use credentials, for example `credentials: "include"` in `fetch`.

Unauthenticated protected calls return `401 {"detail":"Invalid or missing API key"}`. Five failed authentication attempts from one IP within 60 seconds cause `429` with a `Retry-After` header. A saturated database pool returns `503 {"detail":"Database is busy, retry shortly"}` with `Retry-After: 5`. Malformed UUID path values normally resolve to `404`.

### Common response and error conventions

- JSON is used unless the endpoint explicitly returns HTML, PDF, a redirect, or Server-Sent Events.
- Validation errors generated by FastAPI/Pydantic are `422`; explicit business validation is usually `400`.
- Missing records are `404`; duplicates or already-running work are normally `409`.
- Upstream fetch or LLM failures are normally `502`.
- Asynchronous actions return `202` with `{"run_id":"uuid","status":"running"}`. Poll `/api/monitor/run/{run_id}` or the per-job monitor endpoints instead of assuming completion.
- Timestamps are ISO 8601 strings. IDs are UUID strings unless stated otherwise.
- PATCH bodies are partial JSON objects. Fields outside each endpoint's allow-list are ignored unless the endpoint explicitly rejects unknown values.

### Suggested frontend bootstrap

1. Call `GET /health` to confirm the server and version.
2. Call `POST /api/auth/set-session` with the dashboard key and retain cookies.
3. Load `GET /api/settings`, `GET /api/persona`, and the relevant list endpoints.
4. Poll `GET /api/monitor/active` for global work. On job-heavy screens, use `/api/monitor/in-flight?job_ids=...` and `/api/monitor/finished?job_ids=...&since=<epoch-ms>`.
5. For every `202`, show a running state keyed by `run_id`, then resolve it using `/api/monitor/run/{run_id}`.

## Feature 1: API-key authentication and browser sessions

### Files and internal logic

- `backend/main.py:121-314` — owns the authentication middleware, public-route allow-list, constant-time key comparison, cookie creation/deletion, per-IP failure buckets, and all three authentication endpoints below.
- `backend/models/db.py:52` — the `Setting` model stores `dashboard_api_key`; there is no endpoint in this file.
- `backend/config.py` — reads `INITIAL_API_KEY` from the environment as the first-run fallback; no endpoint.
- `backend/seed.py` — seeds the dashboard-key setting and validates writable setting names; no authentication endpoint.

### `POST /api/auth/verify`

Validates a key without creating a cookie. Public. Body: `{"api_key":"string"}`. Returns `200 {"ok":true,"first_run":boolean}`; `first_run` is true when no dashboard key is configured. Wrong or non-string keys return `401`; throttled clients receive `429`. Use this for a login form that wants to validate before changing browser state. Source: `backend/main.py:253`.

### `POST /api/auth/set-session`

Validates `{"api_key":"string"}` and sets the HTTP-only, SameSite-strict `jn_session` cookie for 30 days. Returns `{"ok":true}`. An empty key is accepted only during first-run configuration. Wrong keys return `401`; throttling returns `429`. Use `credentials: "include"`. Source: `backend/main.py:278`.

### `POST /api/auth/logout`

Public endpoint that clears `jn_session`. No body. Returns `{"ok":true}`. Source: `backend/main.py:311`.

### `GET /health`

Public, database-independent liveness check. Returns `{"status":"ok","service":"JobNavigator","version":"2.1.0"}`. Source: `backend/main.py:351`.

### `GET /api/settings`

Returns every setting as one key/value JSON object. Stored JSON is decoded to arrays, objects, and booleans. Secrets return `"••••••"` when configured and `""` when absent. A frontend must preserve the placeholder rather than sending it as a new secret. Source: `backend/api/routes_settings.py:20`.

### `PATCH /api/settings`

Updates several settings from a JSON object. Unknown keys return `400`. Values are validated for types, non-negative integers, five-field cron expressions, and supported enums. Sending `"••••••"` leaves a secret unchanged. Scheduler timing changes are applied immediately; scoring/tailoring concurrency and URL-dedup settings are reloaded. Returns `{"updated":["key"],"warnings":["reconfiguration warning"]}`. Source: `backend/api/routes_settings.py:37`.

### `GET /api/settings/defaults`

Returns the complete seeded defaults map. Use it to implement per-field or global “reset to default” without duplicating defaults in the frontend. Source: `backend/api/routes_settings.py:107`.

### `GET /api/llm/models?provider=<provider>`

Returns a live provider model catalog as `{"models":[{"id","name",...}],"cached":boolean,"stale"?:boolean}`. Supported live providers: `openrouter`, `openai`, `claude_api`, and `claude_code`. OpenAI/Anthropic require a matching configured key; missing keys return `400`, rejected keys or unavailable catalogs return `502`. Results cache for about one hour; OpenRouter entries also include context and token prices. Source: `backend/api/routes_llm.py:86`.

- `extension/content_autofill.js`, `extension/content_autofill_fill.js`, `extension/lib/autofill_match.js`, and `extension/lib/ats_combobox.js` — consume this backend feature from application pages; they define no backend endpoints.

### `GET /api/autofill/config`

Returns extension-facing configuration: flattened persona/profile data, structured persona, Q&A bank, editable field patterns, option synonyms, and autofill limits/settings. The extension should fetch this before scanning a form. Source: `backend/api/routes_autofill.py:265`.

### `POST /api/autofill/answer`

Generates a non-streaming answer. Body supplies `question` (required), plus `company`, `position`, and `max_chars`; persona/Q&A context comes from the database. Returns `{"answer":"text","trimmed":boolean,"max_chars":number}`. Invalid input returns `400`; an unusable LLM response returns `502`. The returned answer is forcibly kept within `max_chars`. Source: `backend/api/routes_autofill.py:367`.

### `POST /api/autofill/answer/stream`

Streaming version of the previous endpoint. It accepts the same fields plus `refinements: string[]`. Response media type is `text/event-stream`. Each event is `data: {"delta":"text"}`; completion is `data: [DONE]`; generation failure is an event containing `{"error":"autofill generation failed"}`. Concatenate deltas in order. Source: `backend/api/routes_autofill.py:398`.

### `POST /api/searches/{search_id}/test`

Starts a non-persisting source test and returns a test `run_id`/running state. It exercises the configured search source, filtering, pagination, and failure reporting without saving jobs. Missing search or unusable configuration returns `404`/`400`; already-running test returns `409`. Source: `backend/api/routes_searches.py:242`.

### `GET /api/searches/test-result/{run_id}`

Polls a search test. Returns a running state until complete, then a result containing source results, sample jobs/counts, filtered counts, and source errors; a failed test includes its sanitized error. Unknown/expired IDs return `404`. Source: `backend/api/routes_searches.py:567`.

## Core data objects for frontend state

### Job

Canonical response fields are `id`, `external_id`, `company`, `title`, `url`, `source`, `search_id`, `description`, `location`, `remote`, `arr_remote`, `arr_hybrid`, `arr_onsite`, `salary_min`, `salary_max`, `salary_source`, `h1b_company_lca_count`, `h1b_company_approval_rate`, `h1b_jd_flag`, `h1b_jd_snippet`, `h1b_verdict`, `cv_scores`, `best_cv`, `scoring_report`, `best_score`, `has_cached_page`, `page_cached_at`, `seen`, `saved`, `status`, `discovered_at`, `has_tailored_resume`, `tailored_resume_id`, `in_flight`, and `in_flight_detail`.

### Résumé JSON

Résumé content is stored as flexible JSON and rendered by templates. The backend expects the main sections used by its templates and LLM flows: `header`, `summary`, `experience`, `education`, and `skills`. Experience entries carry company/title/location/date/description and `bullets`; tailored results may additionally contain `suggested_bullets` for frontend review.

### Asynchronous operation UI

The durable object is `JobRun`: `id`, `job_type`, `trigger`, `status`, `started_at`, `finished_at`, `duration_seconds`, `result_summary`, sanitized `error`, `target_job_id`, and `meta`. A robust frontend should preserve `run_id` after every `202`, poll the specific run, stop on `completed`/`failed`, and then reload the affected entity.

## Backend capabilities without a dedicated public CRUD endpoint

These are implemented backend features but are controlled through settings, triggers, or other feature endpoints:

- APScheduler configures recurring scraping, Gmail checks, backups, Telegram digests, H-1B refresh, cleanup, and automatic rejection.
- Scraper orchestration deduplicates postings by external ID and normalized company/title content hash.
- ATS-specific adapters support Workday, Oracle HCM, Lever, Phenom, TalentBrew, Ashby, Greenhouse, Rippling, Amazon, SmartRecruiters, Meta, Google, and generic career pages.
- JobSpy, Levels.fyi, Jobright, FreeHire, LinkedIn personal/extension, and configured company pages act as discovery sources.
- Salary, location, work arrangement, H-1B eligibility, and résumé-fit analysis enrich jobs.
- Gmail monitoring matches replies to applications and records status transitions; an optional LLM second pass classifies ambiguous mail.
- LLM calls support configured primary/fallback providers, purpose-specific provider/model overrides, prompt caching, concurrency limits, usage/cost logs, and editable prompts.
- Background execution prevents duplicate scoped runs, persists outcomes, sanitizes client-facing errors, and cleans stale runs at startup.
- Database startup creates tables and seeds settings/persona defaults. No Alembic migration layer is present in this repository.
